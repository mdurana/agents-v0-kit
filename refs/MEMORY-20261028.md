# Cross-story memory — 2026-10-28

Two additions to the kit, plus the wiring they need:

1. **All-stories view** (`stories-status.sh`): one read-only table of every story, maintenance note,
   and program record, read from the main checkout **and every git worktree**.
2. **Lessons memory** (`docs/agents-v0/lessons.md`): short lessons a human accepted at the
   local-release gate, read by later stories before they start.

Each change below is tagged `MEM-NN`. The same tag appears in a plain-language comment in every file
it touches (`#` comments in scripts and YAML, `<!-- -->` comments in Markdown prompts). Paths are
relative to the kit root. In an installed project, `templates/.agents-v0/scripts/<x>` becomes
`.agents-v0/scripts/<x>`, `templates/docs/agents-v0/<x>` becomes `docs/agents-v0/<x>`, and
`core/common/{commands,skills,agents,rules}` land under `.cursor/` and `.agents/`.

Base: branch `kitfix-20261022` at `75ca65b`. Nothing here changes `sync-feature-state.sh` or the
state-file schema.

## Design in one paragraph

A story in flight lives in its own worktree (`../<repo>-<feature>` on `feature/<feature>`,
`../<repo>-maintain-<id>` on `maintain/<id>`, created by `feature-worktree.sh`). Its state file is
there, not on main, so `/v0-status` run on main could not see it. `stories-status.sh` reads all
worktrees and stores nothing. Lessons: each phase agent may write up to 3 **candidates** for its phase
into the story's phase-result (`## Lessons` → `### <phase>`), in the story worktree. At
`/v0-local-release` the release-manager copies them into `## Proposed lessons` (`P-1`, `P-2`, … all
`pending`), the user accepts or rejects each one at the release gate, and after the approved merge the
release-manager appends only the accepted ones to `docs/agents-v0/lessons.md` on the integration branch
(ids `L-NNN`, sequential), in the same commit as the release state. Story branches never edit
`lessons.md`. `check-lessons.sh` validates everything and is the guard.

## MEM-01 — `stories-status.sh` and `/v0-status`

**Why.** `/v0-status` read the state files of the checkout it ran in. A story whose phases run in
`../<repo>-<feature>` showed as idle on main (or with a stale copy committed at Intake), and a
maintenance note in `../<repo>-maintain-<id>` did not show at all.

**What changed.**
- New `templates/.agents-v0/scripts/stories-status.sh` (sh + embedded Python, like the other kit
  scripts). Reads `docs/agents-v0/program.state.json`, `onboarding/state.json`,
  `requirements/*.state.json` (not `_state.template.json`), and `maintain/*/state.json` in each
  worktree listed by `git worktree list --porcelain`. One row per story, with columns story, kind,
  branch, worktree (relative to main), activePhase, activeStatus, lastApprovedPhase, verifyPassed,
  reopenCount, tier, blockedReason, lastCommit, note.
  - The row comes from the worktree on the story's own branch (`feature/<feature>`,
    `maintain/<id>`) when there is one, else main, else the first copy. Other copies that disagree are
    named in `note` (`other copy differs: main checkout`). `--all-copies` prints every copy.
  - `lastCommit`: branch tip date for a story read from its own worktree; otherwise the last commit
    that touched its state file.
  - Malformed JSON → row with `note: malformed JSON (line L, column C)`; a story branch whose worktree
    has no state file → `no state file in its worktree`; a worktree folder deleted by hand →
    `worktree folder missing`; not a git repo → reads the current directory only. Never crashes; exit 0
    after printing, exit 2 on a bad option.
  - Writes no files and keeps no cache. Options: `--json`, `--all-copies`, `--root <dir>`.
- `core/common/commands/v0-status.md`: starts by running the script and uses its table as the list
  of open workstreams and as the state of a story whose worktree is not this checkout; do not save the
  output; report `note` rows as is.
- `core/common/rules/workflow-orchestration.mdc` and `AGENTS.md` (Resume row): mention the script.

**How to check.**
```sh
sh scripts/test-memory.sh   # "stories-status:" lines
```
or by hand: in a git repo with `git worktree add -b feature/a ../repo-a main`, put
`docs/agents-v0/requirements/a.state.json` in `../repo-a`, put `{ "feature":` in another worktree's
state file, run `sh templates/.agents-v0/scripts/stories-status.sh` from main and from a worktree:
both list every story, the broken file shows `malformed JSON`, and `git status` is unchanged.

## MEM-02 — `lessons.md` and `lessons-archive.md` templates

**Why.** Lessons from one story (a failure brief, a Verify fail, a re-open, a review finding) stayed
in that story's phase-result and were not seen by the next story.

**What changed.** New `templates/docs/agents-v0/lessons.md` (empty `## Active lessons`) and
`templates/docs/agents-v0/lessons-archive.md` (empty `## Archived lessons`). The how-to, the format,
and an example live in an HTML comment at the top, so the validator ignores them.

Entry format (both files):
```
### L-NNN · YYYY-MM-DD · accepted
- Story/phase: <feature or maintenance id> / <phase>
- Trigger: failure-brief | verify-fail | reopen | review | attempt-budget | blocked | other
- What happened: <one line>
- Do instead: <one line>
- Scope: <which future work it applies to>
```
Archive entries use status `promoted` (plus `- Promoted to: docs/agents-v0/project-profile.md (...)`
or an `docs/agents-v0/adr/*.md` / `docs/agents-v0/design/*.md` path) or `retired` (plus
`- Reason: ...`). Cap: 30 active entries. Ids are unique and sequential across both files.

**How to check.** `cd templates && sh .agents-v0/scripts/check-lessons.sh` → `check-lessons: OK (0 active, 0 archived, ...)`.

## MEM-03 — Lessons rule (always-on)

**Why.** Every phase must know the three rules: read lessons, write candidates in the phase-result,
never write `lessons.md` on a story branch.

**What changed.** `core/common/rules/workflow-orchestration.mdc` gets a `## Lessons Memory
(cross-story)` section: read `## Active lessons` at the start of Plan/Intake/Design/Build/Verify/
Maintain (in a worktree, prefer `git show <integration-ref>:docs/agents-v0/lessons.md`, which has
lessons accepted after the branch was cut); candidate format
`- Trigger: … · What happened: … · Do instead: … · Scope: …` under `## Lessons` → `### <phase>`, at
most 3 per phase, or `- none`; keep earlier phases' subsections when rewriting the file; accepting
happens only at `/v0-local-release`. `AGENTS.md` gets one conduct line. Always-on size after the
change: about 21.6 KB of the 32 KB limit (`validate-kit.sh` §16).

**How to check.** `grep -n "Lessons Memory" core/common/rules/workflow-orchestration.mdc`;
`sh scripts/validate-kit.sh` passes the always-on budget check.

## MEM-04 — `check-lessons.sh`

**Why.** The memory has to stay small, well-formed, and free of secrets, and the "never on a story
branch" rule needs a deterministic check, not only a prompt.

**What changed.** New `templates/.agents-v0/scripts/check-lessons.sh`. Default run checks
`docs/agents-v0/lessons.md`, `lessons-archive.md`, and every `requirements/*.phase-result.md` and
`maintain/*/phase-result.md`:
- heading format, required bullets, allowed status per file, known Trigger;
- ids unique, rising within each file, and sequential (no gaps) across both files;
- active cap (default 30; `--max-active N` or `LESSONS_MAX_ACTIVE`);
- size per entry or candidate (default 800 characters; `--max-chars N` or `LESSONS_MAX_CHARS`);
- secrets scan (private key blocks, AWS/GitHub/GitLab/Slack/Google keys, `sk-…`, JWTs, credentials in
  URLs, `password|secret|token|api_key = <value>` with placeholders such as `<…>`, `${…}`, `***`
  allowed); the message gives the line, never the value;
- phase-result `## Lessons`: only `### <phase>` subsections for story phases, at most 3 candidates per
  phase, each with Trigger/What happened/Do instead/Scope;
- phase-result `## Proposed lessons`: `- P-N · pending|accepted|rejected · <phase> · Trigger: … ·
  What happened: … · Do instead: … · Scope: …`; with `--decided`, no `pending` left;
- `--unchanged-since <ref>`: fails when `lessons.md`/`lessons-archive.md` changed on this branch since
  `<ref>` (committed, uncommitted, or untracked);
- `--next-id` prints the next free id (e.g. `L-004`); `--phase-result <file>` limits the phase-result
  scope; `--root <dir>`.
Exit 0 pass, 1 fail (plain `FAIL:` lines), 2 usage.

**How to check.** `sh scripts/test-memory.sh` ("check-lessons:" lines cover good files, bad heading,
missing bullet, duplicate id, id gap, promoted without pointer, wrong status, unknown trigger,
oversize entry, fake GitLab token, password assignment, placeholder allowed, 31 entries vs cap 30,
`--max-active`, `LESSONS_MAX_ACTIVE`, 3 vs 4 candidates, missing fields, unknown phase, `- none`, fake
AWS key, pending vs `--decided`, malformed proposal, maintain phase-result, and the branch guard).

## MEM-05 — Phase prompts read lessons and write candidates

**Why.** The memory is useless unless phase agents read it, and the candidates must come from the
agents that saw the problem.

**What changed.**
- `/v0-plan`: reads `lessons.md` with the profile and passes it to `program-planner`. Plan is a
  program phase on main and writes no candidates.
- `/v0-intake`, `/v0-design`, `/v0-build`, `/v0-verify`, `/v0-maintain`: read the lessons memory at
  the start and pass matching entries to the phase subagents; the phase-result step now includes
  `## Lessons` → `### <phase>` (≤ 3 or `- none`). Build names failure briefs and exhausted attempt
  budgets as likely candidates; Verify writes candidates whether it passes or re-opens.

**How to check.** `grep -l "docs/agents-v0/lessons.md" core/common/commands/v0-{plan,intake,design,build,verify,maintain}.md`
lists all six (also enforced by `validate-kit.sh`).

## MEM-06 — `/v0-local-release` proposes, the user decides, the merge appends

**Why.** Only a human should decide what becomes cross-story memory, and only the integration branch
should hold it, so parallel stories never conflict on `lessons.md`.

**What changed.** `core/common/commands/v0-local-release.md` (new step 3, renumbered 4–6),
`core/common/skills/local-release/SKILL.md` (steps 6 and 9, one more "Do not"), and
`core/common/agents/release-manager.md` (item 1a):
1. In the story checkout, before the gate: `check-lessons.sh --unchanged-since <integration-ref>
   --phase-result <phase-result>` (stop on exit 1), add ≤ 3 `### release` candidates, copy all
   candidates into `## Proposed lessons` as `P-<n> · pending`, run the check again.
2. At the gate the user is asked to approve the release **and** to accept or reject each `P-<n>`.
   No explicit accept → marked `rejected` → not appended.
3. After the merge, in the integration checkout, before the release-state commit: mark decisions
   (accepted when explicitly accepted, rejected otherwise), `check-lessons.sh --decided --phase-result <file>`,
   append accepted entries with ids from `check-lessons.sh --next-id`, run `check-lessons.sh`; over the
   cap → ask the user what to archive (never drop). `lessons.md` goes into the release-state commit.

**How to check.** Read the three files; `validate-kit.sh` asserts `check-lessons.sh` is named in
`/v0-local-release` and `## Proposed lessons` in the `local-release` skill.

## MEM-07 — `install.sh` installs and updates the new files

**Why.** New scripts and templates must reach existing projects.

**What changed.** `scripts/install.sh`: `stories-status.sh` and `check-lessons.sh` added to the
installed list and to the `--update` always-overwrite list; `lessons.md` and `lessons-archive.md`
added to the installed list only (seeded when missing, never overwritten by `--update`). Linked
installs (`--link`) symlink `.agents-v0/scripts`, so they get the scripts with no change; their
lessons templates are seeded by `install_templates` as before.

**How to check.** `sh scripts/test-memory.sh` installs into a fresh git repo and checks both scripts
are executable, both docs exist, and both scripts run there. `validate-kit.sh --target <project>`
also checks them.

## MEM-08 — Editing `lessons.md` asks the user

**Why.** A deterministic guard in the edit hook, so a phase agent on a story branch cannot quietly
write into the memory.

**What changed.** `core/common/hooks/hook-policy.py` `classify_path` and shell write checks (`_segment_writes_ask_path` / `_heredoc_writes_ask_path`): `docs/agents-v0/lessons.md`
and `lessons-archive.md` return `ask` with a message pointing to the phase-result `## Lessons`
section, and `_commit_paths_are_evidence` allows including `lessons.md`/`lessons-archive.md` in an evidence-only release-state commit. `scripts/test-hook-policy.py`: four new path cases and five new shell cases. Shell commands for the new scripts stay
`allow` (read-only).

**How to check.** `python3 scripts/test-hook-policy.py` → `OK (251 cases)`.

## MEM-09 — GitLab CI `lessons-check` job and `pre-push` hook

**Why.** Teams using `/v0-release` (remote MR) or `git push` with `--git-hooks` should get the same check.

**What changed.** `templates/.gitlab-ci.yml`: new `lessons-check` job (stage `delivery-gate`, merge
requests only) runs `check-lessons.sh`, and on `feature/*` / `maintain/*` source branches also

**How to check.** `python3 -c 'import yaml; print(yaml.safe_load(open("templates/.gitlab-ci.yml"))["lessons-check"]["script"])'`;

## Not done / open questions

- **Remote release (`/v0-release`)** does not propose or append lessons. After a human merges on
  GitLab there is no kit step on the integration branch to append accepted lessons. Options: a
  follow-up `/v0-local-release`-style "record lessons" step, or append on the next story's Intake.
- **Program and onboarding phases** (roadmap, architecture, plan, onboard) read lessons but write no
  candidates: they run on main with no release gate of their own.
- **Appended in the release-state commit, not inside the `--no-ff` merge commit.** The kit's merge
  step and its commit approvals are unchanged; the accepted lessons land in the commit right after the
  merge (the same commit as the release state.json and phase-result).
- **Stale `lessons.md` in a worktree.** A worktree's copy is as of its branch point. The rule tells
  agents to prefer `git show <integration-ref>:docs/agents-v0/lessons.md`; nothing enforces it.
- **Secrets scan is pattern-based.** It catches common token shapes and `password = value`; it is
  not a replacement for the CI secret detection job.
- **The `ask` on `lessons.md` edits** also fires for the release-manager's legitimate append; that is
  intended (a human sees the change). In a non-interactive runner the append needs an allow rule.
