# local-release

Primary local completion for the `release-manager` agent (`workflow-orchestration.mdc`, `/v0-local-release`). `/v0-release` is optional when the user wants to push or open a remote merge request.

## Steps
1. Confirm `"verifyPassed": true` and `"verify"` is in `approvedPhases` (or for `P0-A`, `verifyPassed` is `true` and the user is approving the single P0-A release gate now). A maintenance note with `tier: "emergency"` may proceed when `maintain` is approved and the note records a rollback plan and `Follow-up verify due`. If Verify has not passed and neither exception applies, stop and run `/v0-verify` first.
2. Ensure verify reports, test evidence, and the artifact (`docs/agents-v0/requirements/<feature>.md` or `docs/agents-v0/maintain/<id>/note.md`) are tracked on disk. Only when non-doc files changed after `verifyPassed: true` does the change go back through Verify (`sh .agents-v0/scripts/sync-feature-state.sh --reopen verify --verify-passed false <artifact>`).
3. Sync `README.md` or sequence diagrams when the feature changed user-facing setup or flows. Update `CHANGELOG.md` via `sh .agents-v0/scripts/release-notes.sh <artifact> --include-unreleased --insert CHANGELOG.md` when the profile uses a changelog.
4. Resolve the final verify command with `sh .agents-v0/scripts/run-backend-verify.sh "Backend verify"` and/or `"Frontend verify"`, then execute the printed command. The script only prints. If it prints nothing, use the layout default. Stop when the tree is not green, and do not mark the work released.
5. Resolve the integration branch with `sh .agents-v0/scripts/resolve-integration-branch.sh`.
<!-- MEM-06: lesson candidates become proposed lessons at this gate; the user decides each one; accepted ones are appended to docs/agents-v0/lessons.md in the integration checkout after the merge. -->
6. Proposed lessons: run `sh .agents-v0/scripts/check-lessons.sh --unchanged-since <ref from step 5> --phase-result <phase-result>`; exit 1 stops the release (a story branch never edits `docs/agents-v0/lessons.md`). Add at most 3 `### release` candidates under `## Lessons`, then copy every candidate into `## Proposed lessons` as `- P-<n> · pending · <phase> · Trigger: … · What happened: … · Do instead: … · Scope: …` (or `- none`), and run the check again. Then write `docs/agents-v0/requirements/<feature>.phase-result.md` (or `docs/agents-v0/maintain/<id>/phase-result.md`) with `phase: release`, `status: awaiting_approval`, then run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase release --status awaiting_approval <artifact>`. Stop for explicit user approval. Do not infer it. Ask the user to accept or reject each `P-<n>` in the same message.
7. After that approval, commit any pending delivery evidence or changelog files when the user authorizes the commit. For `Story: P0-A`, do not merge. `HEAD` must already be the integration ref from step 5. If it is not, stop. Commit on that branch. For every other story, when the current branch is a feature branch separate from the integration branch, use the ref from step 5. When `git worktree list` shows that ref checked out in another worktree, `cd` to that worktree and merge there. Do not run `git checkout <ref>` inside the feature or maintain worktree. Merge on user confirmation. A feature story's branch is `feature/<feature>` from Intake: first commit the release preparation on it (`<story>: release approved`), then squash-merge it (`git merge --squash feature/<feature>`, one squash commit with the `Story-Branch` / `Story-Tip` trailers that `--approve release` prints; kitfix-20261031-gate-commit). A standard or emergency maintenance note's branch is `maintain/<id>` (`git merge --no-ff maintain/<id>`). A trivial note is already on the integration branch and does not merge. If the merge fails or conflicts, stop and do not mark the work released.
   - <!-- kitfix-20261031-keep-branches --> Keep the story branch after the release: never delete or rename `feature/<feature>` or `maintain/<id>` (the hooks block it); `git worktree remove <path>` removes only the folder.
8. Once the merge succeeds (or when already on the integration branch, including `P0-A`), in that integration checkout, run `sh .agents-v0/scripts/sync-feature-state.sh --approve release <artifact>`, update that phase-result file to `status: approved`, do step 9, and then commit the updated state file on user confirmation. `--approve release` records the earlier phases. The next story may start at `/v0-intake`. `/v0-release` is optional.
<!-- MEM-14: check-lessons.sh --approval-text compares the marks and lessons.md with the user's approval message. -->
9. In that integration checkout, before the commit in step 8: mark each `P-<n>` `accepted` (when explicitly accepted by the user) or `rejected` (when rejected or not mentioned in the user's release approval), run `sh .agents-v0/scripts/check-lessons.sh --decided --phase-result <phase-result>`, append each accepted one to `## Active lessons` in `docs/agents-v0/lessons.md` using the file edit tool (not shell redirection) as `### L-NNN · <today> · accepted` (id from `check-lessons.sh --next-id`) with the `Story/phase`, `Trigger`, `What happened`, `Do instead`, and `Scope` bullets, run `sh .agents-v0/scripts/check-lessons.sh`, then `sh .agents-v0/scripts/check-lessons.sh --phase-result <phase-result> --approval-text '<the user's release approval message, verbatim>'` (exit 1: fix the marks or `lessons.md` from its `FAIL` lines; never reword the approval), and commit `lessons.md` with the release state. Over the active cap: ask the user what to move to `docs/agents-v0/lessons-archive.md`.

<!-- kitfix-20261029-step4-p1e: after the merge, no commit or state change on the story branch; check it is fully merged; list every commit. -->
10. After the release-state commit (feature stories), run `sh .agents-v0/scripts/check-release-evidence.sh <artifact>` in the integration checkout. Exit 1 (for example `feature/<feature>` is not fully merged into the integration branch): report its `FAIL` lines and stop; do not merge again and do not name the next story.
11. Final summary: list every commit made in this turn (short SHA, branch, subject), on every branch and worktree.

## Do not
- Commit to `feature/<feature>` or `maintain/<id>` after it was merged into the integration branch, or run `sync-feature-state.sh` (any option) or edit its state, phase-result, or evidence in the feature or maintain worktree after the merge. Release approval happens only on the integration branch; `sync-feature-state.sh --approve release` refuses on any other branch.
- Call `glab` or push: the hook refuses push and `glab` writes; the user pushes from their own terminal, or runs `/v0-release`, which gives them the push and MR commands.
- Merge or approve a merge request.
- Treat `/v0-release` as required for this local completion.
- Edit `docs/agents-v0/lessons.md` on a feature or maintain branch, or append a lesson the user did not accept.
