# /v0-build

You are entering the **Build** phase of the delivery lifecycle (`workflow-orchestration.mdc`).

## Prerequisite
On Intel macOS, run `sh .agents-v0/scripts/host-tools-macports.sh` before the baseline. Exit 2 means a tool named by the bound pack's `hostChecks` (or JDK 21 and Node when no pack is bound yet), or PyYAML, is missing. Stop and ask the user to approve `sh .agents-v0/scripts/host-tools-macports.sh --install`. PyYAML follows the same script (`docs/agents-v0/gold-standards.md`). Pack `java` keeps Maven at `./mvnw`. Docker and Podman are not MacPorts ports.

Read the `Pack` cell in `docs/agents-v0/project-profile.md`. Any story stops when `Pack` is empty, still a placeholder, or has no complete `.agents-v0/packs/<id>/pack.json`, and returns to `/v0-architecture`. Before launching build agents, read `docs/agents-v0/requirements/<feature>.phase-result.md` when it exists. For P0-A, do not require a requirements artifact, a Design approval, or an existing lock: the P0 skeleton section writes the requirements file from the milestone, then the N/A design, and pins it. Then `--verify-lock` applies. For any other story whose `design.md` records `N/A: no /api/v1 operation`, with no `ux-spec.md` and no OpenAPI draft, `design.lock` is enough; the Design row is written with the Build approval. `Material: yes` does not use that shortcut: stop until `sh .agents-v0/ci/check-arc.sh <artifact>` passes and Design is approved. Otherwise confirm the Intake artifact records explicit Design approval and names the approved contract/ADR/diagram paths (and, for UI-affecting changes, the approved `docs/agents-v0/design/<feature>/ux-spec.md` plus the `docs/agents-v0/design/<feature>/mockups/` files that spec links). If that evidence is missing, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase build --status blocked --reason "<one line>"` when the artifact exists, then stop and report it; do not infer approval. For P0-A, write and pin first (P0 skeleton), then run `sh .agents-v0/ci/check-design.sh <feature> --verify-lock`. Every other story runs that check now. The design must still match the pinned design. If it does not, stop and follow `/v0-design` Amending an approved design. On a brownfield repo also read the `docs/agents-v0/onboarding/modules/` document for each touched module.

## Resume
For P0-A, the P0 skeleton section creates `docs/agents-v0/requirements/<feature>.md` (slug p0-a-platform-skeleton) before this sync. Then run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase build --status in_progress`. If this phase is already `in_progress` or `blocked`, continue from files on disk; do not recreate them. On a red baseline or exhausted fix attempts, re-run with `--status blocked --reason "<one line>"` and stop. When the gate is ready for the user, re-run with `--status awaiting_approval` and stop. Do not add an `Approved` row until the user approves. If this phase's approval row says `Re-opened` (`/v0-deliver`), the phase is open again: reset the affected `AC-*` rows in `docs/agents-v0/build/<feature>/plan.md` to `pending`, write or update the failing test assertions first, run the fast verify command to record a new red attempt card in `build-report.md` and refresh `red-tests.json` (`sh .agents-v0/ci/check-build-plan.sh <feature> --record-red`) before applying the green fix, remove any stale untracked `docs/agents-v0/verify/<feature>/` reports from the earlier commit, and set `Approved` only after the user approves the re-run.

## Collision
Before the first edit, follow `workflow-orchestration.mdc` Parallel features. If `git status` shows another feature's code or a shared-file edit that is not this feature's approved diff, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase build --status blocked --reason "<paths>"` and stop. (Untracked `docs/agents-v0/verify/<feature>/` files left by a rejected Verify pass of this same feature are not another feature's collision; remove them on a re-opened Build.) Do not rewrite `docs/agents-v0/project-profile.md` from this feature.

## Instructions
1. **Baseline first:** Skip this run when `git status --porcelain` is empty and `git rev-list --count origin/<default>..HEAD` is `0`. That checkout is the default branch tip, or behind it, with no local edits. Otherwise run the full Backend verify or Frontend verify command from `docs/agents-v0/project-profile.md` **before any edit** (`Service verify` with the story's `Service root:` when the profile lists `Service roots`). If it fails because a module that already exists fails, stop and report the pre-existing failure; never build on a broken baseline. The P0 platform-skeleton story (P0-A) is the exception: a missing module or a failing seeded starter is the work, not a broken baseline. Continue and fix or create it. On that story, replace every `TEMPLATE:` line in `docs/agents-v0/architecture.md` and `docs/agents-v0/network.md` with what this commit contains. Both files must exist. A network row is `built` only when a file in the commit shows that port or dependency; otherwise leave it `planned` with an empty citation. Do not describe a planned row as running. Then `sh .agents-v0/scripts/check-onboarding-docs.sh docs/agents-v0/architecture.md docs/agents-v0/network.md` must pass. Any other story stops on a failed baseline and does not rewrite those shared files.
2. **Wire the quality gate before implementing** if the repo has not wired it. The `java` example uses `maven/quality-plugins.xml` (JaCoCo/Checkstyle/SpotBugs/OWASP bound to `verify`), `maven/contract-conformance.xml`, and `maven/archunit/LayerRulesTest.java` — unwired tooling makes `./mvnw -B clean verify` compile-only. Any other pack wires the coverage and test reports named in its `pack.json`.
3. Launch the build agents per the Design artifacts:
   - `backend-engineer` (skill: `implement-service`) follows the installed service skill. P0-A follows that pack's scaffold skill. Extract `templates/app/p0-platform-skeleton.tar.gz` only when that pack's scaffold says to.
   - `bff-engineer` (skill: `implement-bff`) for the BFF. The installed skill is the one for this pack.
   - `frontend-engineer` (skill: `implement-frontend`) for the bound pack's `ui` id, implementing the approved UX spec: per-screen state matrix, component default behavior, layout from the linked HTML mockups, and accessibility. The real API client lives in the app and calls only the OpenAPI operation named on each component row. Mockups stay static design artifacts.
4. When `docs/agents-v0/design/<feature>/openapi.yaml` exists, the contract-owning engineer merges that approved draft into the org catalog (`openapi/api-v1.yaml`, or the catalog path in the profile) before service implementation edits — or right after capturing `--record-red` when a plan row tests the catalog itself. Stop if that catalog is already modified by another feature. A story with no draft records N/A in the build report. Merge with `sh .agents-v0/ci/check-openapi.sh merge docs/agents-v0/design/<feature>/openapi.yaml <catalog>` (it rewrites the catalog's formatting: review the diff) or by hand, then prove it: `sh .agents-v0/ci/check-openapi.sh merged docs/agents-v0/design/<feature>/openapi.yaml <catalog>` (which also lints the combined catalog) and `sh .agents-v0/ci/check-openapi.sh lint <catalog>` must pass. In a vertical slice the backend merges the contract first, then the BFF, then the frontend; each re-runs its baseline.
5. Before the first implementation edit, write `docs/agents-v0/build/<feature>/plan.md`: one row per approved `AC-*` (AC, Status `pending`/`done`/`blocked`, Test). Mark a row `done` only after that unit's fast command is green, and name the test. Do not add, delete, or rewrite AC rows (`workflow-orchestration.mdc`).
6. Each agent works the plan **exactly as its `implement-*` skill step 6** (red–green, real fast-verify profile cell, `sh .agents-v0/ci/check-build-plan.sh <feature> --record-red` before the green run, attempt cards, `check-attempt-budget.sh`, no `build-output.txt` re-read). Do not restate that loop here. When the budget is spent, sync `--status blocked --reason "attempt budget exhausted"` and stop.
   - Units the requirements artifact marks as security-review triggers (auth, RBAC, upload, public route) or that implement a saga or consumer (`implement-messaging`) run on the Plan-role model, not the Build-role model (`docs/agents-v0/model-routing-matrix.md` Critical units). When `.cursor/model-config.json` exists, take its `plan` value and strip any `[...]` modifier suffix (for example `grok-4.7`) for the subagent launch override; if the host subagent launcher does not accept that slug as a launch override, omit the override so the subagent uses its frontmatter model.
7. The second red result for the same test writes `docs/agents-v0/build/<feature>/failure-brief.md` (`helper: debug-investigator`) and returns. Launch `debug-investigator` from this session, pass the note back, run `sh .agents-v0/scripts/check-failure-brief.sh <feature>`, then let the engineer take attempt three. A third red result stops. Launch each failure brief once.
7a. A flaw in the approved design (a missing operation, a wrong field, an authorization rule that cannot hold) is not fixed in place. Set the phase `blocked` (reason "design amendment") and follow `/v0-design` Amending an approved design.
8. Each agent then runs the full profile verify command once (Backend verify, or Frontend verify for a UI-only change) with **bounded fix attempts (≤ 3 per failure)**. On exhaustion, stop and present the blocker; hand security-critical or complex units to `solution-architect` for a design review instead of a further attempt. The fast loop does not replace this gate.
9. Check the **Build gate** (`workflow-orchestration.mdc`):
   - Baseline green on the full verify command; the gate run is that same full command, with the quality plugins executed (coverage/static/CVE fail machine-side). The fast command is only the red–green loop.
   - Approved feature draft merged into the org catalog (`.agents-v0/ci/check-openapi.sh merged` and `.agents-v0/ci/check-openapi.sh lint <catalog>` pass), or N/A recorded.
   - Mechanical checks pass: `sh .agents-v0/ci/check-build-plan.sh <feature> --complete` (every AC has a row; each done row names an existing test and has a red card first; when `red-tests.json` exists, that test name is in the captured report). `REQUIRE_RED_REPORT` stays off unless the project sets it. Also `sh .agents-v0/ci/check-endpoint-auth.sh <base>` (no new endpoint without the pack's auth marker; the pack's public marker marks a public one on purpose), `sh .agents-v0/ci/check-frontend-calls.sh` (the frontend calls only catalog operations), and `sh .agents-v0/ci/check-design.sh <feature> --verify-lock`.
   - New/changed behavior covered by tests; contract-conformance diff has no breaking change (or a recorded N/A reason); the pack's `layerCheck` where `pack.json` names one (Pack `java`: ArchUnit).
   - Methods ≤ 30 lines; cognitive complexity ≤ 15.
   - Every endpoint has authentication and authorization using the pack's auth marker. A public route uses the pack's public marker. `check-endpoint-auth.sh` reads that pack's `pack.json`.
   - Correlation ID and `traceparent` wired in.
   - DTOs only at the edge; migrations use the pack `migrationTool`, written with `migration-safety` (expand/contract). When the diff touches a migration or SQL file and `DIFF_BASE` is set, a test must run against the database named in the profile. H2 does not satisfy `.agents-v0/ci/check-gate-metrics.sh`. A missing down script stays legal when the rollback note is recorded.
   - No secrets in code; log values sanitized.
   - UI changes implement the approved UX spec: per-screen state matrix, component defaults (including an override when one is recorded), layout matching the linked mockups, WCAG 2.1 AA a11y, design-system conformance. API integration uses the named OpenAPI operations. It does not add endpoints the contract does not list.
10. Evidence commits, in this order. Ask once: that approval covers the code commit and the reports commit. Do not stop between them for a second chat approval. The hook still asks on each `git commit`. `.agents-v0/ci/check-evidence.sh` ignores later doc-only commits and rejects non-doc changes after the stamped SHA.
    1. Commit the code.
    2. Write `docs/agents-v0/build/<feature>/build-report.md` with `commit:` set to that full SHA (command, result, per-criterion **file:line citations**, and the attempt cards). Optional `build-output.txt` — prefer CI artifacts for raw logs (no secrets). Do not read that log back on the next attempt.
    3. Commit the reports and feature state with `git commit -m "<message>" -- docs/agents-v0/build/<feature> docs/agents-v0/requirements/<feature>.state.json` (include `docs/agents-v0/requirements/<feature>.state.json` when present). That path is the evidence commit: the hook does not ask again. Do not change code after the stamp. A stamp for an earlier tree, or reports left uncommitted while code moved on, is stale.
11. **Stop** and present the gate result to the user with the evidence citations (per criterion: file:line; per tool: command + result). Write `docs/agents-v0/requirements/<feature>.phase-result.md` (`workflow-orchestration.mdc` Phase result: `status: awaiting_approval` when stopping at the gate, updated to `status: approved` after the user approves). After explicit approval, append the Build decision (Decision: `Approved`), approver, date, changed-area summary, and the `docs/agents-v0/build/<feature>/` evidence paths to the Intake artifact's `Delivery approvals` section. When this story followed No contract (`design.md` records `N/A: no /api/v1 operation`, no `ux-spec.md`, no OpenAPI draft, no `asyncapi.yaml`, and no `events/` files) and it is not P0-A, append the Design row in that same approval, with the same approver and date. Its Artifacts cell is `N/A: no /api/v1 operation` and the `design.md` path. Do not advance to Verify without that approval. The local delivery gate runs once, at Release.
