## Instructions
1. **Baseline check:** Unless the working tree is clean at the default branch tip, resolve the command with `sh .agents-v0/scripts/run-backend-verify.sh "Backend verify"` or `"Frontend verify"`, then execute the printed command before editing. The script only prints. If it prints nothing, use the layout default. If the baseline is broken outside `known_failures`, run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase build --status blocked --reason "Baseline broken outside known_failures" docs/agents-v0/requirements/<feature>.md` and stop.
2. **Build plan (`plan.md`):** Before the first implementation edit, write `docs/agents-v0/build/<feature>/plan.md` with one row per approved `AC-*` (`AC`, `Status` `pending`/`done`/`blocked`, `Test`, `Risk` `standard`/`critical`).
3. **Contract catalog merge:** When `docs/agents-v0/design/<feature>/openapi.yaml` exists, merge the approved operations and schemas into the repo catalog (`openapi/api-v1.yaml` or `openapi/<service>-v1.yaml`).
4. **Execute implementation units (`implement-*` skills):**
   - Launch the engineer subagent matching each unit's surface: `backend-engineer` (`implement-service`), `bff-engineer` (`implement-bff`), or `frontend-engineer` (`implement-frontend`).
   - **Critical-unit model routing:** For units touching authentication, authorization, uploads, public routes, cryptography, ledger/money, or message consumers/sagas (`implement-messaging`), use the `plan` model from `.cursor/model-config.json` (`docs/agents-v0/model-routing-matrix.md` Critical units).
   - Follow strict **red-to-green TDD**: write the failing test first, run the profile's fast verify command, log the attempt card in `docs/agents-v0/build/<feature>/build-report.md`, implement the minimal code to pass, and mark the `plan.md` row `done` with the test name.
   - **Host tools and database runtime:** Never run `sudo`/`doas` or a system package manager (`apt`, `apt-get`, `dnf`, `yum`, `apk`, `zypper`, `pacman`, `brew`, `port`), and never point `DOCKER_HOST` at a TCP socket. Before the first test that needs a database (Testcontainers, a migration test), run `sh .agents-v0/scripts/check-database-runtime.sh --phase build docs/agents-v0/requirements/<feature>.md`. It checks, in order, a working container runtime (docker, then podman), embedded PostgreSQL declared in the build, and a portable PostgreSQL (`initdb` + `pg_ctl` on `PATH` or under `$PG_HOME`). Use the runtime it prints. Exit 3 (`runtime=none`): run the `Next:` command it prints (`--status blocked --reason "Database runtime unavailable"`), report what is missing, and stop. Do not install a database or a container runtime.
5. **Bounded failure & debug loop:**
   - Before each new attempt, run `sh .agents-v0/scripts/check-attempt-budget.sh docs/agents-v0/build/<feature>/build-report.md` (max 8 failed attempts). If it exits 1, run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase build --status blocked --reason "Attempt budget spent" docs/agents-v0/requirements/<feature>.md` and stop.
   - If the same test fails twice consecutively, write `docs/agents-v0/build/<feature>/failure-brief.md` (`helper: debug-investigator`, `outputs:`, `return:`, `ask:`, the failing test name, and a `file:line`), run `debug-investigator` from this session, verify with `sh .agents-v0/scripts/check-failure-brief.sh <feature>`, and allow one final attempt. A third consecutive failure stops Build (prompt-only; `check-failure-brief.sh` does not count it). Record `sh .agents-v0/scripts/sync-feature-state.sh --active-phase build --status blocked --reason "Third consecutive failure" docs/agents-v0/requirements/<feature>.md` and stop.
   - If implementation reveals a flaw in the approved design, stop and follow `/v0-design` (Amending an Approved Design).
6. **Full native verify gate:** Resolve the command with `sh .agents-v0/scripts/run-backend-verify.sh "Backend verify"` and/or `"Frontend verify"`, then execute the printed command. The script only prints. If it prints nothing, use the layout default. After a Maven verify, run `sh .agents-v0/scripts/check-tests-ran.sh` (kitfix-20261031-tests-ran): exit 1 means test classes exist but none ran, or an `*IT.java` class has no Surefire/Failsafe report. Treat it as a failed verify; fix the plugin setup or the naming, never skip it. Confirm:
   - All tests pass, coverage meets the project bar, and static/security checks wired into the pack build succeed.
   - Every endpoint has explicit authentication/authorization (or the pack's intentional public marker on public routes).
   - DTOs are used at API boundaries, migrations follow `migration-safety`, and no secrets or unsanitized log values exist.
   - Record the final verify command output summary and per-AC `file:line` citations in `docs/agents-v0/build/<feature>/build-report.md`, and the raw verify output in `docs/agents-v0/build/<feature>/build-output.txt`. Do not read `build-output.txt` on the next attempt. The full-verify fix cap is ≤ 3 attempts per failure (prompt-only).
7. **Standard Build gate stop:** Write `docs/agents-v0/requirements/<feature>.phase-result.md` (`phase: build`, `status: awaiting_approval`, and `## Lessons` → `### build` with at most 3 candidates or `- none`; a failure brief or an exhausted attempt budget in this Build is a likely candidate) and run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase build --status awaiting_approval docs/agents-v0/requirements/<feature>.md`.
8. **Stop** and present the Build report and `file:line` citations to the user. After explicit user approval:
   - Update `<feature>.phase-result.md` to `status: approved`.
   - Run `sh .agents-v0/scripts/sync-feature-state.sh --approve build docs/agents-v0/requirements/<feature>.md`.
   - <!-- kitfix-20261031-traceability --> The approval runs `check-traceability.sh build`: every `operationId` / path of `docs/agents-v0/design/<feature>/openapi.yaml` must have code under `app/` (T4) and at least one test that names it or calls the path (T5). Report each `TRACE WARN` line (check, earliest bad phase) to the user.
   - <!-- kitfix-20261031-gate-commit --> **Commit the gate on `feature/<feature>`** with the command the script prints (`git add -A && git commit -m "<story>: build approved"`), only when the user authorizes `git commit`.
