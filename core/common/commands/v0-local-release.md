# /v0-local-release

You are entering the **local release** checkpoint (`workflow-orchestration.mdc`). It is optional. After Verify, `/v0-release` may run without it. It does not open a merge request and it does not complete Release (it does not change the story's milestone manifest Status; `/v0-release` sets it to `done`).

## Prerequisite
Before launching the release manager, read `docs/agents-v0/requirements/<feature>.phase-result.md` when it exists. The feature artifact needs an `Approved` verify row, and non-doc files are unchanged since the verify reports' `commit:` lines (or `commit:` equals `HEAD`; matching `.agents-v0/ci/check-evidence.sh`). A report's `commit:` header names the verified code/test commit, not the subsequent doc commit that records the report or approval row. For `Story: P0-A` with `Milestone: P0`, `docs/agents-v0/verify/<feature>/test-report.md` with no non-doc changes since `commit:` is enough; Intake, Design, Build, and Verify rows are written at the approval below. A maintenance note does not use this command: run `/v0-release`. If the feature evidence is missing, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase release --status blocked --reason "<one line>"` when the artifact exists, then stop.

## Resume
Run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase release --status in_progress` (which synchronizes `.state.json` and updates `docs/agents-v0/requirements/<feature>.phase-result.md` to `phase: release`, `status: in_progress`). If this checkpoint is already `in_progress` or `blocked`, continue from files on disk. On a blocker, re-run with `--status blocked --reason "<one line>"` and stop. For a story with existing Approved Intake, Design, Build, and Verify rows, ensure the verify reports and the Intake artifact (`<artifact>`) are committed in `HEAD` (`git cat-file -e "HEAD:<path>"` and `git diff --quiet HEAD -- <path>`; if untracked or uncommitted on disk with no non-doc changes since `commit:`, commit them without changing `commit:`), then run the local gate (`sh .agents-v0/scripts/check-delivery-gate-local.sh <feature> --base <that-ref>`). If the local gate fails, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase release --status blocked --reason "<failure-summary>"` and stop; never set `awaiting_approval` on a failing local gate. Only when the local gate has passed, re-run with `--status awaiting_approval` and stop. For P0-A when any of `intake`, `design`, `build`, or `verify` is still missing from `Delivery approvals`, stop for explicit approval first, backfill each missing row among `intake`, `design`, `build`, and `verify` with Decision `Approved` in canonical order (`intake`, `design`, `build`, `verify`, `release`) while keeping any row already set to `Approved`, append `release` with Decision `Local`, write the phase result and cleared state, commit the reports, artifact, phase result, and state together, and run the gate (`sh .agents-v0/scripts/check-delivery-gate-local.sh <feature> --base <that-ref>`); if the gate fails, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase release --status blocked --reason "<failure-summary>"`, write `status: blocked` in the phase result, and stop; never leave or set `awaiting_approval`. Do not write the `Local` row until the user approves. If the release row's Decision is already `Local`, check if the checkpoint is complete (`--clear-active` has run, `docs/agents-v0/requirements/<feature>.phase-result.md` records `phase: release`, `status: local`, and both are committed in `HEAD`): if complete, stop and name `/v0-release` for this story; if incomplete, resume the remaining commit, fast-forward, phase-result, and `--clear-active` steps. The next story starts with `/v0-intake` from the integration branch. If the release row is `Approved`, stop: this story is past the checkpoint.
