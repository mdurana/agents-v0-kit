# /v0-verify

You are entering the **Verify** phase of the delivery lifecycle (`workflow-orchestration.mdc`).

## Prerequisite
Before launching verification agents, read `docs/agents-v0/requirements/<feature>.phase-result.md` when it exists. Confirm the change was explicitly approved by its producing phase: the linear path requires Build approval in the Intake artifact's `Delivery approvals`, and the `docs/agents-v0/build/<feature>/` evidence paths that row records must exist. For `Story: P0-A` with `Milestone: P0`, the build report with `commit:` is enough; the Build approval row is written at Release. A maintenance change (`docs/agents-v0/maintain/<id>/note.md`; use `<id>` wherever `<feature>` appears below, and the note as `<artifact>`) requires an `Approved` `maintain` row in the note. If evidence is missing, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase verify --status blocked --reason "<one line>"` when the artifact exists, then stop and report it; do not infer approval.

## Resume
Run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase verify --status in_progress`. If this phase is already `in_progress` or `blocked`, continue from files on disk; do not recreate them. On a blocker, re-run with `--status blocked --reason "<one line>"` and stop. When the gate is ready for the user, re-run with `--status awaiting_approval` and stop. Do not add an `Approved` row until the user approves. If this phase's approval row says `Re-opened` (`/v0-deliver`), the phase is open again: continue from the files, and set `Approved` only after the user approves the re-run.

When reports already exist under `docs/agents-v0/verify/<feature>/` and every `commit:` line equals `HEAD`, and this re-entry changes no application code and no tests, quote the test run in `test-report.md`. On a full Verify, write only a missing `vapt-checklist.md` or `review-notes.md`. Do not launch `test-engineer` again. Abbreviated Verify still skips `security-reviewer` and `code-reviewer`. When `HEAD` differs from a report's `commit:`, run this command's Verify for that story again and stamp the new SHA. When that Verify row is `Approved`, set its Decision to `Re-opened` before the re-run, and set `Approved` only after the user approves again.

## Collision
Before the first edit, follow `workflow-orchestration.mdc` Parallel features. If `git status` shows another feature's code or a shared-file edit that is not this feature's approved diff, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase verify --status blocked --reason "<paths>"` and stop.

## Instructions
Re-entry follows Resume. Reports whose `commit:` lines equal `HEAD`, with no code or test change, keep `test-report.md` and add only a missing reviewer report.
0. Each Verify report must start with provenance headers: `commit: <full-sha>` (tree verified), `kit-version:` (from `.agents-kit-version` if present), `agent:` (role name). When Verify adds or changes tests, commit those first (the hook asks). Stamp the reports with that SHA, then commit them with `git commit -m "<message>" -- docs/agents-v0/verify/<feature>`. That second commit does not ask again. Security and code review, when they run, use that same code commit.
1. Launch the `test-engineer` subagent (skill: `quality-gate`) unless Resume says the reports already match `HEAD`:
   - Write AAA tests; cover happy/error/edge paths.
   - Use Testcontainers + Pact where the repo already depends on them. A migration or SQL change still needs a test against the profile database; H2 does not satisfy `check-gate-metrics.sh` when `DIFF_BASE` is set.
   - **Helpers.** If `docs/agents-v0/verify/<feature>/helper-brief.md` exists, launch the helper it names (`schema-author` unless the brief says otherwise) from this session. Pass the result into a second launch of `test-engineer`. Delete the brief after that result is back. Launch each brief once (`workflow-orchestration.mdc` Helper agents).
   - When `git rev-parse HEAD` equals the `commit:` line in `docs/agents-v0/build/<feature>/build-report.md` and this phase is not adding or changing tests, do not run the full verify command again. Do not re-run `check-design.sh`, `check-build-plan.sh`, `check-endpoint-auth.sh`, or `check-frontend-calls.sh`. Quote that build run in the test report. Still run `sh .agents-v0/ci/collect-gate-reports.sh <root>` and set both `DIFF_BASE="$(sh .agents-v0/scripts/resolve-integration-branch.sh)"` and `REQUIRE_CVE_REPORT=1` when running `sh .agents-v0/ci/check-gate-metrics.sh <root>` for each layout root. Pack `java` also runs OWASP Dependency-Check. Other packs refresh the file named by `cve.path` in `pack.json` via `collect-gate-reports.sh`. If this phase adds or changes tests, commit them first (step 0), then run the profile Backend verify command once on that new commit (Pack `java`: `./mvnw -B clean verify`) or the full frontend verify command and confirm coverage ≥ 80% backend / 70% frontend on the report. CI fails changed lines under 80% (or `docs/agents-v0/quality-gates.md`) for every pack when `DIFF_BASE` is set. Whole-module line coverage fails when the pack wires it (Pack `java`: JaCoCo 0.80), when a Whole-module lines row in `docs/agents-v0/quality-gates.md` sets the bundle minimum, or when `MIN_LINE_PCT` is set. A `coverage_ratchet` row does not change that JaCoCo minimum.
   - Run the machine checks CI runs, so a failure shows here and not after the push. For each layout root (Backend root, BFF root, and each Service root), run `sh .agents-v0/ci/collect-gate-reports.sh <root>` first (refreshes `cve.path` for `.NET`, `Node`, and `Python` when not already produced by the verify command), then set both flags together: `DIFF_BASE="$(sh .agents-v0/scripts/resolve-integration-branch.sh)" REQUIRE_CVE_REPORT=1 sh .agents-v0/ci/check-gate-metrics.sh <root>` (executed tests, diff coverage, and a present CVE report with no unsuppressed HIGH/CRITICAL). Omit both flags only when this story's Out of scope names a later story id in the same milestone whose user story wires coverage and CVE scanning, and that story has no Approved Verify row yet. The seeded P0 skeleton binds that gate in the same story, so it does not use this skip. The test report must quote that story id and say diff coverage and the CVE report were skipped until it. Any other story sets both flags. When this phase added or changed tests, or `HEAD` is not the build report's commit, also run `sh .agents-v0/ci/check-design.sh <feature> --verify-lock` and `sh .agents-v0/ci/check-build-plan.sh <feature> --complete` when the story has a design and a plan; `sh .agents-v0/ci/check-endpoint-auth.sh <base>` and `sh .agents-v0/ci/check-frontend-calls.sh`. Quote their results in the test report; the report does not replace them. When `HEAD` is that commit and no tests changed, quote the build run for those four checks.
   - When this story is the P4 SLO story, or the requirements artifact cites `docs/agents-v0/design/system/nfr-slo.md`, follow `slo-evidence` and write `docs/agents-v0/design/system/slo-evidence.md`.
   - For an integration story, a vertical slice, a P2 journey, or a P4 story, follow `e2e-perf-testing` and persist `docs/agents-v0/verify/<feature>/e2e-report.md`.
   - Pack `java` runs OWASP Dependency-Check when `REQUIRE_CVE_REPORT=1` is set, so `dependency-check-report.json` exists. Other packs refresh the file named by `cve.path` via `sh .agents-v0/ci/collect-gate-reports.sh <root>`. No new high/critical CVEs without a documented exception. When both metric flags are omitted under the quality-story deferral above, do not run the scan; the test report quotes the deferral instead.
   - For UI-affecting changes: run the automated accessibility check (axe-core) on changed routes of the built UI, not on the Design HTML mockups; confirm no serious/critical violations; cover each UX acceptance criterion from `docs/agents-v0/design/<feature>/ux-spec.md` with a test of the built UI; persist the UX report to `docs/agents-v0/verify/<feature>/ux-report.md` (violations with severity and file:line, UX acceptance criteria status).
   - Persist the test report to `docs/agents-v0/verify/<feature>/test-report.md` (build status, coverage numbers, CVE scan results, documented exceptions).
2. After the test engineer has finished and any helper brief is gone, launch `security-reviewer` (skill: `vapt-review`) and `code-reviewer` (skill: `pr-review`) together. When Resume says the reports already match `HEAD`, launch a reviewer only when its report is missing, and go on to step 3 when both reports exist. Each writes only its own report. Wait for both before routing anywhere, including when one report already contains a Critical finding.
   - Security: always-on VAPT findings F4, F8, F9, and F10, plus regression findings for the affected surface (`vapt-review`). An applicable miss on an always-on finding is **Critical**. HIGH and MEDIUM regression findings block merge when the diff touches that surface. LOW regression findings block only when the diff makes the issue exploitable. N/A only for an unaffected surface, with the reason. Persist `docs/agents-v0/verify/<feature>/vapt-checklist.md` (finding ID, pass/fail/N/A + reason, evidence file:line, retest step).
   - Review: `code-review.mdc`, labels Critical/Suggestion/Nice to have. Persist `docs/agents-v0/verify/<feature>/review-notes.md` (finding, label, file:line, rule clause).
3. Gather one Critical list from both reports into `docs/agents-v0/requirements/<feature>.phase-result.md`.
4. Check the **Verify gate** (`workflow-orchestration.mdc`):
   - Quality: build green, coverage met for changed code, no new high/critical CVEs without a documented exception. P4 SLO story: `docs/agents-v0/design/system/slo-evidence.md` has a measurement or a waiver for every filled NFR/SLO row.
   - Security: applicable always-on findings (F4, F8, F9, F10) have no Critical findings. Applicable HIGH and MEDIUM regression findings pass. Applicable checks cannot be waived as N/A.
   - UX: for UI-affecting changes, automated a11y check green (no serious/critical violations) and UX acceptance criteria covered; N/A only when the change has no UI surface, with the reason recorded.
   - Review: no Critical findings.
   - Evidence: the reports exist under `docs/agents-v0/verify/<feature>/`.
5. On any Critical finding in the gathered list, route back to the responsible Build/Maintain agent and re-enter Verify after the fix.
6. **Stop** and present the gate result to the user. Write `docs/agents-v0/requirements/<feature>.phase-result.md` (`workflow-orchestration.mdc` Phase result) before stopping, including when status is `blocked`. After explicit approval, append the Verify decision (Decision: `Approved`), approver (the GitLab username of the person approving, for example `@ada`: CI may bind the merge request approval to this row), date, the `docs/agents-v0/verify/<feature>/` report paths, and documented CVE exceptions as a row in the delivery record's `Delivery approvals` table — the Intake artifact for the linear path, or the `verify` row of the maintenance note. Do not advance to Release without that approval. The next command is `/v0-release`. `/v0-local-release` may be run instead; it is not required.

## Abbreviated Verify (P0 skeleton)

When the requirements artifact contains `Story: P0-A` and `Milestone: P0`, only `test-engineer` runs (skill `quality-gate`). When `HEAD` already matches the build report `commit:` and no tests are added, quote that run instead of a second full verify. Otherwise run the full verify command once. Then run `sh .agents-v0/ci/collect-gate-reports.sh <root>` and `.agents-v0/ci/check-gate-metrics.sh` for each layout root (Backend root, BFF root, and each Service root) with both flags set, and write `docs/agents-v0/verify/<feature>/test-report.md` with `commit:`. `security-reviewer`, `code-reviewer`, the UX audit, and `e2e-perf-testing` are skipped. Do not ask for approval and do not write an Approved row. Run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase release --status in_progress`. The next command is `/v0-release`, which still waits for `glab mr create` to return a URL and records this approval with the others from that one approval. `/v0-local-release` may be run instead; it records Intake, Design, Build, and Verify, and `/v0-release` then records only the Release row. Any other story uses the full Verify below.

## Abbreviated Verify (Tier trivial)
For a maintenance note with `Tier: trivial`, after `sh .agents-v0/ci/classify-change.sh <base> --require-trivial` passes, only `test-engineer` runs (skill `quality-gate`): the full verify command, `.agents-v0/ci/check-gate-metrics.sh` for each changed layout root, and a CVE re-scan for a dependency bump. Persist `docs/agents-v0/verify/<id>/test-report.md` with `commit:`. `security-reviewer`, `code-reviewer`, the UX audit, and `e2e-perf-testing` are skipped. The moment the classifier stops saying eligible, the abbreviated path ends: set `Tier: standard` (a person confirms) and run the full Verify. For `Tier: emergency`, this Verify is owed by the note's `Follow-up verify due` date; run the full Verify then.
