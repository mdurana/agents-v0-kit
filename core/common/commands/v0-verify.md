# /v0-verify

You are entering the **Verify** phase of the delivery lifecycle (`workflow-orchestration.mdc`).

## Prerequisite & Resume
1. If `<feature>` or `<id>` was not given, follow the naming rule in `workflow-orchestration.mdc` Parallel Features. Do not set `in_progress` until it resolves. Read `docs/agents-v0/requirements/<feature>.state.json` (or `docs/agents-v0/maintain/<id>/state.json` when verifying a maintenance note; use `<id>` for `<feature>` and `docs/agents-v0/maintain/<id>/note.md` as `<artifact>`). A feature story with `release` in `approvedPhases` stops. Do not reopen it. A docs-only edit or a 1-for-1 patch bump starts at `/v0-triage`. Any other fix starts at `/v0-maintain`. A new feature starts at `/v0-intake` with a new slug. A maintenance note is a different record and is not this stop, except a note that already has `release` approved and is not an emergency note that still owes Verify: stop and start a new `<id>`. For a feature story, run `git worktree list` and look for branch `feature/<feature>`. For a standard or emergency maintenance note, look for `maintain/<id>` only when `release` is not in `approvedPhases`. If that worktree exists and this checkout is not it, stop. Open that folder and run `/v0-status <feature>` or `/v0-status <id>` there. <!-- kitfix-20261031-branch-guard --> If no worktree has branch `feature/<feature>` for a feature story (Intake step 7 did not run), stop: do not set `in_progress` and do not work on the integration branch. Tell the user that `/v0-intake <feature>` must finish its feature-worktree step (branch authorisation, then `sh .agents-v0/scripts/feature-worktree.sh <feature>`). `sync-feature-state.sh` refuses Verify for a feature story off `feature/<feature>`. A released emergency note that still owes Verify stays in the integration checkout.
2. Confirm the producing phase is approved in `.state.json` (`build` in `approvedPhases` for a feature story, or `maintain` in `approvedPhases` for a maintenance note). If missing, run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase verify --status blocked --reason "Build/Maintain not approved" <artifact>` and stop.
3. If `verify` is already in `approvedPhases`, stop and suggest `/v0-local-release`, unless non-doc files changed after Verify. In that case run `sh .agents-v0/scripts/sync-feature-state.sh --reopen verify --verify-passed false <artifact>` instead of `--active-phase verify --status in_progress`. Otherwise run `sh .agents-v0/scripts/sync-feature-state.sh --active-phase verify --status in_progress <artifact>`.
<!-- MEM-05: phase agents read the accepted cross-story lessons before they start, and leave lesson candidates in the phase-result at the gate (workflow-orchestration.mdc Lessons Memory). -->
4. Read the lessons memory (`docs/agents-v0/lessons.md`, `workflow-orchestration.mdc` Lessons Memory) and pass entries whose `Scope` matches to `test-engineer`, `security-reviewer`, and `code-reviewer`.

## Collision
Check `git status` (`workflow-orchestration.mdc` Parallel Features). Stop if another feature's uncommitted changes are present.

## Instructions
1. **Quality Gate (`test-engineer`, skill: `quality-gate`):**
   - Resolve layout roots via `eval "$(sh .agents-v0/scripts/resolve-layout.sh)"`. Resolve the verify command with `sh .agents-v0/scripts/run-backend-verify.sh "Backend verify"`, `"Service verify"`, and/or `"Frontend verify"`, then execute the printed command. The script only prints. If it prints nothing, use the layout default. After a Maven verify, run `sh .agents-v0/scripts/check-tests-ran.sh` (kitfix-20261031-tests-ran): exit 1 means test classes exist but none ran, or an `*IT.java` class has no Surefire/Failsafe report. Treat it as a failed verify; fix the plugin setup or the naming, never skip it.
   - Before a verify command that needs a database, run `sh .agents-v0/scripts/check-database-runtime.sh --phase verify <artifact>` (container runtime, then embedded or portable PostgreSQL). Exit 3: run the `Next:` command it prints (`--active-phase verify --status blocked --reason "Database runtime unavailable"`), report what is missing, and stop. Never use `sudo`, a system package manager, or a Docker TCP socket to get one.
   - Verify that every `AC-*` in `docs/agents-v0/requirements/<feature>.md` (or Acceptance in `docs/agents-v0/maintain/<id>/note.md` for a maintenance note), including negative and edge ACs, has a passing test, changed-line coverage meets `docs/agents-v0/quality-gates.md` (default $\ge 80\%$ changed lines; whole-module $\ge 80\%$ backend / $\ge 70\%$ frontend), and no unsuppressed HIGH/CRITICAL dependency vulnerabilities remain.
   - For UI changes, verify automated accessibility checks (axe-core) and UX acceptance criteria from `docs/agents-v0/design/<feature>/ux-spec.md`, writing `docs/agents-v0/verify/<feature>/ux-report.md`.
   - For integration stories, vertical slices, P2 journeys, or P4 stories, follow `e2e-perf-testing` (`docs/agents-v0/verify/<feature>/e2e-report.md`) and `slo-evidence` (`docs/agents-v0/design/system/slo-evidence.md`) when applicable.
   - Write `docs/agents-v0/verify/<feature>/quality-gate.md` summarizing test execution, coverage, and AC traceability.
   - When `docs/agents-v0/verify/<feature>/helper-brief.md` exists, launch `schema-author` from this session and delete the brief. The phase agent already synced the primary artifact.
2. **Abbreviated Verify (`Tier: trivial`):**
   - When a maintenance note has `tier: "trivial"`, skip step 3 (`security-reviewer` and `code-reviewer`) once `test-engineer` and the native verify command pass.
   - A maintenance note with `tier: "emergency"` is full Verify, owed by the note's `Follow-up verify due` date, and is not this shortcut.
3. **Role-Separated Security & Code Review (`security-reviewer` + `code-reviewer`):**
   - Launch `security-reviewer` (skill: `vapt-review`) and `code-reviewer` (skill: `pr-review`) against `git diff <baseCommit>...HEAD` (using `baseCommit` from `.state.json`), `docs/agents-v0/requirements/<feature>.md` (or `docs/agents-v0/maintain/<id>/note.md` for a maintenance note), and `design/<feature>/` when that directory exists. A maintenance note may have no design directory; that absence is not a failed Verify. (In single-agent IDEs, execute `vapt-review` and `pr-review` sequentially.)
   - `security-reviewer` checks always-on VAPT controls (`F4` access control, `F8` same-role `{id}` access → 403 or 404, `F9` JWT `alg`/`iss`/`aud`/`exp` with a fail-closed blacklist, `F10` audit events without a token) plus surface-specific findings and writes `docs/agents-v0/verify/<feature>/vapt-checklist.md`.
   - `code-reviewer` checks `code-review.mdc` and stack pack rules, labeling findings `Critical`, `Suggestion`, or `Nice to have`, and writes `docs/agents-v0/verify/<feature>/code-review.md`.
4. **Evaluate Verdict:**
   - Gather any `Critical` findings across `quality-gate.md`, `vapt-checklist.md`, and `code-review.md` into `docs/agents-v0/requirements/<feature>.phase-result.md` (or `docs/agents-v0/maintain/<id>/phase-result.md` for a maintenance note). Add `## Lessons` → `### verify` with at most 3 candidates or `- none`, whether Verify passes or re-opens (a Critical finding that sends the story back is a `verify-fail` or `reopen` candidate).
   - **If any `Critical` finding exists:** When the note is `tier: "emergency"` and `release` is already in `approvedPhases`, do not run `--reopen maintain`. Run `sh .agents-v0/scripts/sync-feature-state.sh --verify-passed false --active-phase verify --status blocked --reason "Critical finding in owed emergency verify; start a new maintenance id" <artifact>` and stop. The next command is `/v0-maintain` with a new `<id>`. Otherwise run `sh .agents-v0/scripts/sync-feature-state.sh --verify-passed false --reopen build <artifact>` (or `--reopen maintain` for a maintenance note that is not released) and route back to `/v0-build` (or `/v0-maintain`). If `sync-feature-state.sh` exits 2 (`reopenCount > 3`), stop and escalate to the user.
   - **If zero `Critical` findings exist:** Write that phase-result file (`phase: verify`, `status: awaiting_approval`), then run `sh .agents-v0/scripts/sync-feature-state.sh --verify-passed true --active-phase verify --status awaiting_approval <artifact>`.
5. **Stop** and present the Verify reports (`quality-gate.md`, `vapt-checklist.md`, `code-review.md`) to the user. After explicit user approval:
   - Update that phase-result file to `status: approved`.
   - Run `sh .agents-v0/scripts/sync-feature-state.sh --verify-passed true --approve verify <artifact>`.
   - <!-- kitfix-20261031-traceability --> The approval runs `check-traceability.sh verify`: every `AC-<n>` needs a passing row in `quality-gate.md` (T6). A missing or failing AC is blamed on the earliest phase where it is lost (Design when `design.md` does not trace it, Build when no test names it, else Verify). Report each `TRACE WARN` line to the user.
   - <!-- kitfix-20261031-gate-commit --> **Commit the gate on `feature/<feature>`** with the command the script prints (`git add -A && git commit -m "<story>: verify approved"`), one commit, never `--amend`. `/v0-local-release` does not start while Verify work is uncommitted.
   - Next command: `/v0-local-release` (primary local workflow) or `/v0-release` (optional remote MR workflow).
