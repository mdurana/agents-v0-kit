# /v0-design

You are entering the **Design** phase of the delivery lifecycle (`workflow-orchestration.mdc`).

## Prerequisite
Before launching the architect, read `docs/agents-v0/requirements/<feature>.phase-result.md` when it exists. When the artifact contains `Story: P0-A` and `Milestone: P0`, follow instruction 0 and do not launch the architect. Otherwise confirm the Intake requirements artifact exists and its `Delivery approvals` section records an explicit Intake approval. If either is missing, and the artifact exists, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase design --status blocked --reason "<one line>"`, then stop and report the missing evidence; do not infer approval. On a brownfield repo the architect also reads the as-is documents: `docs/agents-v0/architecture.md`, `docs/agents-v0/design/system/context-map.md`, the `docs/agents-v0/onboarding/modules/` documents for the touched modules, and `docs/agents-v0/discovery/endpoints.txt` for existing operations the draft could clash with.

## Resume
When the artifact exists, run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase design --status in_progress`. If this phase is already `in_progress` or `blocked`, continue from files on disk; do not recreate them. On a blocker, re-run with `--status blocked --reason "<one line>"` and stop. When the gate is ready for the user, re-run with `--status awaiting_approval` and stop. Do not add an `Approved` row until the user approves. If this phase's approval row says `Re-opened` (`/v0-deliver`), the phase is open again: continue from the files, and set `Approved` only after the user approves the re-run.

When `docs/agents-v0/design/<feature>/design.lock` exists, follow Amending an approved design. When `docs/agents-v0/design/<feature>/design.md` is already on disk and the Design row is not `Approved`, skip steps 1-5. Run the mechanical checks (step 6) and the design review (step 7). A failing check is an open Critical. Launch `solution-architect` or `ux-designer` only to fix an open Critical, then run the checks and `design-reviewer` again so `review.md` names the current design hash.

## Collision
While another feature is in flight in this checkout, write only `docs/agents-v0/requirements/<feature>.md`, its state file, and `docs/agents-v0/design/<feature>/`. The feature contract draft is `docs/agents-v0/design/<feature>/openapi.yaml`. Do not edit the org catalog (`openapi/api-v1.yaml`, or the catalog path in the profile) during Design. Stop before editing any other shared file (`workflow-orchestration.mdc` Parallel features) when `git status` shows it is already modified or another feature's state is `in_progress`, `awaiting_approval`, or `blocked` on a phase that writes it. Record `--status blocked` with that reason.

## Instructions
Re-entry follows Resume. A `design.lock` uses Amending an approved design. An existing `design.md` with no `Approved` Design row starts at step 6.
0. **P0-A.** When the artifact contains `Story: P0-A` and `Milestone: P0`, do not launch `solution-architect`. Run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase build --status in_progress` and stop. `/v0-build` writes the N/A design and pins it.
1. Launch the `solution-architect` subagent with the Intake artifact. Resume skips this step when `design.md` is already on disk or `design.lock` exists.
2. **Helpers.** When the story adds a `/api/v1` operation, launch `schema-author` from this session in the same turn as `solution-architect`. Tell it to write `docs/agents-v0/design/<feature>/openapi.yaml` and, when the story has events, `docs/agents-v0/design/<feature>/events/`. Do not wait for the architect to return a helper brief for that draft. A brief is only for a helper that could not be named until mid-phase (a second red test, or doc-sync). If a brief is already on disk, launch the helper it names, pass the result back, and delete the brief. Launch each brief once. Do not present the gate while a brief remains.
3. For UI-affecting changes, launch the `ux-designer` subagent (skill: `ux-design`) after the feature draft `docs/agents-v0/design/<feature>/openapi.yaml` exists, or immediately when this story records `N/A` for the contract. Run the helper step again if that agent leaves a brief. Produce `docs/agents-v0/design/<feature>/ux-spec.md` and static HTML mockups under `docs/agents-v0/design/<feature>/mockups/`. The spec includes user flows, a per-screen state matrix (loading/error/empty/success) linked to those mockups, per-component default behavior (name, screen, mockup, OpenAPI operation or `—`, default behavior, override), WCAG 2.1 AA accessibility requirements, a responsive/device matrix, design-system conformance, and UX acceptance criteria. Mockups do not call the API, and every interactive element carries `data-component="<name>"`. A component that calls the API names an operation in `docs/agents-v0/design/<feature>/openapi.yaml`.
4. For **Major** tier changes, when `docs/agents-v0/architecture.md` has an `Approved` `architecture` row, cite that pack and do not rewrite it, including an Accepted ADR. A changed recommendation supersedes that ADR and amends the ARC record. When that row is absent (a single ticket, not a program), the architect follows `system-design`.
4b. When the requirements artifact says `Material: yes`, follow the ARC steps in `contract-first-design`. Write or cite `docs/agents-v0/design/system/arc-record.md`. Record `ARC:` on the requirements artifact. Run `sh .agents-v0/ci/check-arc.sh docs/agents-v0/requirements/<feature>.md` before the Design gate. The `arc` approval is separate from the Design approval. A material story does not use the No contract shortcut.
5. The architect must follow the `contract-first-design` skill and produce:
   - A feature OpenAPI 3.0 draft at `docs/agents-v0/design/<feature>/openapi.yaml` only when the story adds or changes a `/api/v1/` operation. A story with no such operation does not add a draft: `design.md` records `N/A: no /api/v1 operation` (name the reason). `check-design.sh` allows the missing file. Do not invent a path so the draft will lint. The org catalog stays unchanged until Build.
   - Event schemas under `docs/agents-v0/design/<feature>/events/` with `eventVersion`; additive evolution.
   - One error envelope per API surface (RFC 7807 **or** custom — not mixed).
   - Idempotency keys on non-idempotent creates.
   - `docs/agents-v0/design/<feature>/design.md` from `docs/agents-v0/design/_design.template.md`: traceability of every AC and NFR, data model, an authorization matrix with the resource rule per operation, failure modes that name every `Kind: negative` and `Kind: edge` id, observability, and rollout.
   - An ADR for non-trivial decisions, with the real alternatives and Status `Proposed` or `Accepted`. When the reviewer is skipped, `ADR: N/A: no product decision` is enough. Do not invent a second alternative for that case. An Accepted ADR is superseded by the next file when the decision changes. Do not rewrite it. `sh .agents-v0/ci/check-adr.sh` must pass.
   - Mermaid diagrams following `architecture-and-diagrams.mdc` conventions when the story has a contract, a UI, or a public route. When the reviewer is skipped, do not add a diagram.
6. **Mechanical checks.** Run, and fix until each passes: `sh .agents-v0/ci/check-design.sh <feature>`; `sh .agents-v0/ci/check-adr.sh`; when `docs/agents-v0/design/<feature>/openapi.yaml` exists, `sh .agents-v0/ci/check-openapi.sh lint` on that file and `sh .agents-v0/ci/check-openapi.sh compat` against the catalog when the catalog exists; for UI changes `sh .agents-v0/ci/check-ux-spec.sh <feature>`.
7. **Design review.** Launch the `design-reviewer` subagent when the story has a `/api/v1` draft, a UX spec, or a public route that is not only health, readiness, or liveness. It writes `docs/agents-v0/design/<feature>/review.md`. Route each Critical finding back to the `solution-architect` (or `ux-designer`), then run the reviewer again: the review must name the design's current hash. Skip the reviewer when `design.md` records `N/A: no /api/v1 operation`, there is no `ux-spec.md`, and any public marker is only on `/health`, `/ready`, or `/live` (Pack `java`: `@PreAuthorize("permitAll()")`; other packs use the public marker in their `PACK.md`). Another public route still needs the reviewer. `check-design.sh --pin` accepts the pin without `review.md` in the skip case.
8. Check the **Design gate** (`workflow-orchestration.mdc`):
   - When the story adds a `/api/v1/` operation, the feature draft `docs/agents-v0/design/<feature>/openapi.yaml` exists and event schemas under `docs/agents-v0/design/<feature>/events/` are defined with `eventVersion`. When it does not, `design.md` records `N/A: no /api/v1 operation` and there is no draft. The org catalog is not part of this gate.
   - The mechanical checks above pass. When `review.md` exists, it has no open Critical finding. When the reviewer was skipped, `review.md` is absent and `--pin` still succeeds.
   - Error envelope chosen per surface when the story has an API.
   - An ADR with at least two alternatives and Status `Proposed` or `Accepted` when the reviewer runs. When the reviewer is skipped, the line is `ADR: N/A: no product decision`. The pin requires `Accepted`.
   - Mermaid diagrams when the story has a contract, a UI, or a public route. When the reviewer is skipped, none are required.
   - Security-review triggers identified; brief threat-model notes (assets, trust boundaries, top risks) for non-trivial security. Name the applicable always-on VAPT findings (F4, F8, F9, F10).
   - UX spec and HTML mockups exist for UI-affecting changes: flows, per-screen state matrix, a component-default row for every interactive control, a11y requirements, responsive/device matrix, design-system conformance, UX acceptance criteria. `ci/check-ux-spec.sh` passes, and API-backed components name an operation in the feature draft.
9. **Stop** and present the gate result to the user, including the feature draft path, `design.md`, the UX spec path, the mockup paths, and the review's open Suggestions. Write `docs/agents-v0/requirements/<feature>.phase-result.md` (`workflow-orchestration.mdc` Phase result). After explicit approval, set the cited ADR's Status to `Accepted` when it is still `Proposed`, append the Design decision (Decision: `Approved`), approver, date, and contract/design/ADR/diagram/UX-spec/mockup paths to the Intake artifact's `Delivery approvals` section, then pin the approved design: `sh .agents-v0/ci/check-design.sh <feature> --pin "approved"`. The contract path in that row is `docs/agents-v0/design/<feature>/openapi.yaml`, or `N/A: no /api/v1 operation` when there is no draft. Do not advance to Build without that approval, unless No contract applies.

## No contract
When `design.md` records `N/A: no /api/v1 operation`, there is no `ux-spec.md` and no OpenAPI draft, and any `permitAll` is only on `/health`, `/ready`, or `/live`: run the checks and pin with `--pin "approved"`. Do not ask for approval and do not write an Approved row. Run `sh .agents-v0/scripts/sync-feature-state.sh <artifact> --active-phase build --status in_progress`. The next command is `/v0-build`. That approval writes the Design row with the Build row, same approver and date. A `/api/v1` draft, a UX spec, or any other public route still stops at step 9. `Material: yes` also stops at step 9. Cite the program ARC record when the `architecture` row already names it. Add an `arc` row only when this story amends that recommendation. Then take the Design approval. A new service or a new security boundary is `Material: yes`, so this shortcut does not apply to it.

## P0 skeleton
Do not run this phase. Instruction 0 hands the story to `/v0-build`, which writes the N/A design and pins it. Release writes the Design row with the other four.

## Amending an approved design
Build, Verify, or a review may find the approved design wrong. Do not edit the design in place and carry on. Set the phase `blocked` (reason "design amendment"), then follow `docs/agents-v0/design/_amendments.template.md`: change the files, run the checks, and run `design-reviewer` on the design as it stands. `review.md` names the current hash and has no open Critical before the amendment row is presented. Add a row to `docs/agents-v0/design/<feature>/amendments.md` with the first 12 characters of `sh .agents-v0/ci/check-design.sh <feature> --hash`, get the user's explicit approval on that row, and pin it (`--pin "amendment <n>"`). The pin covers `design.md`, the contract draft, `events/`, `ux-spec.md`, `mockups/`, and the ADR named on the `ADR:` line. A changed decision does not edit that ADR's Decision or Alternatives. Set its Status to `Superseded by ADR <NN>`, write the successor with Status `Accepted`, point `design.md` at the successor, and run `sh .agents-v0/ci/check-adr.sh`. CI (`ci/check-design.sh --verify-lock`) rejects a design or cited ADR that changed without an Approved amendment row.
